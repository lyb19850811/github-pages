**「MySQL + Redis 双写一致性」是被问滥了的题，但多数答案缺一个前提。** 本文先立一个判断，再往下推：

> **任何非原子的双写都不可能保证强一致，除非阻塞读写（加锁/事务）。所以缓存架构追求的是「最终一致性」——先问业务能不能容忍短暂不一致，再选方案。**

## 结论先行

1. **本质**：Redis 作为缓存，是用「短暂不一致」换「高并发读」。一致性要求越严，越不该让缓存承载写路径。
2. **写路径的黄金法则**：**先更新数据库，再删除缓存**（Cache-Aside / 旁路缓存）。删缓存而非更新缓存。
3. **为什么删不更新**：删除是无状态操作、并发安全；更新是有状态操作，会被并发写「写覆盖」，还可能缓存了永远没人读的数据。
4. **两种极端并发漏洞**（先更库后删缓存、先删缓存后更库）都存在，只是概率不同——先更库后删缓存的窗口极窄，是工程上的默认选择。
5. **兜底链路演进**：缓存过期时间 → 延迟双删 → MQ 重试 → binlog 订阅（Canal/Maxwell）CDC。每一层都是补前一层删不干净的缝。
6. **强一致场景（库存、余额）**：不靠缓存双写，靠 DB 事务 + 条件写（版本号/`FOR UPDATE`），缓存只做读旁路。

## 一、什么场景需要双写：先问三个问题

缓存不是免费的，每引入一份缓存就多一份一致性债务。上线前先回答：

| 问题             | 判断依据                                             |
| -------------- | ------------------------------------------------ |
| **读多写少吗？**     | 缓存收益来自「一次写、N 次读」。写多读少时缓存只添乱，纯读多才值得缓存             |
| **有热点吗？**      | 缓存的价值是扛热点（如秒杀商品的详情、文章详情、排行榜），冷数据缓存是浪费内存          |
| **能容忍短暂不一致吗？** | 能 → 走最终一致（绝大多数）；不能（余额、库存、订单状态）→ 缓存只做读旁路，写走 DB 事务 |

**关键：一致性要求是连续的，不是二选一的。** 面试里最该先做的一件事是「声明业务背景」——实时性要求多高、允许多久的延迟。阿里云开发者社区那篇《Redis 常见面试题》反复强调：**「一定、一定、一定要设置前提」**。

反例：库存扣减。腾讯云那篇《探索 Redis 与 MySQL 的双写问题》给的例子——用户 A/B 同时抢最后一件库存，若缓存里的库存没及时减，B 看到的还是「有 1 件」而下单，就会**超卖**。这种场景就不能依赖「最终一致」，必须让写路径走 DB 事务，缓存只作读加速。

## 二、架构演进：从无缓存到最终一致的五步

### 阶段 0：无缓存，直查 DB

读压力全压数据库。性能瓶颈出现后，第一反应是加缓存。

### 阶段 1：Cache-Aside（旁路缓存），应用层自己管缓存

最主流、代码侵入最小。**应用自己维护 DB 与缓存的读写**：

```
读：先查缓存 → 命中直接返回 → 未命中查 DB → 回填缓存
写：先更新 DB → 再删除缓存（不是更新！）
```

这是 Azure Architecture Center 官方定义的 [Cache-Aside 模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)，也是绝大多数业务的地基。

### 阶段 2：+ 延迟双删，补并发漏洞

先更库后删缓存仍有极窄的并发窗口（见第四节），延迟双删再删一次作兜底：

```
1. 更新 DB
2. 删除缓存
3. 休眠 T（如 1s）
4. 再次删除缓存
```

### 阶段 3：+ MQ 重试，保证「删除」最终被执行

「删缓存失败」是延迟双删和 Cache-Aside 共有的缺口。解法：删除失败 → 把 key 丢进 MQ → 消费者重试删除，直到成功。借助 MQ 的重试/死信机制达到最终一致。

### 阶段 4：binlog 订阅 CDC，解耦 + 工业级兜底

不靠业务代码删缓存，而是**监听 MySQL 的 binlog**，由 Canal / Maxwell 解析变更，投递到 MQ，消费者异步删缓存：

```
MySQL 变更 → binlog → Canal/Maxwell → MQ(Kafka) → 消费者 → 删除 Redis 缓存
```

好处：业务代码零侵入、删除失败由 MQ 重试保证、天然覆盖所有写路径（含绕过应用直改 DB 的情况）。代价：引入 Canal + MQ 两套中间件，链路变长。

### 阶段 5：强一致（一致性要求高的场景）

放弃「双写最终一致」，改用：

| 手段                        | 说明           | 代价                       |
| ------------------------- | ------------ | ------------------------ |
| DB 事务 + 行锁 / `FOR UPDATE` | 行即资源，事务内保证原子 | 只覆盖单库范围                  |
| 条件写 / 版本号（CAS）            | 写带版本，拒绝旧版本覆盖 | 需应用改造                    |
| 分布式锁（读写锁）                 | 写串行化         | **性能差，基本失去了缓存的意义，业界不推荐** |

> **一句话：强一致业务别用缓存双写，用 DB 事务 + 条件写；缓存只做读旁路。**

## 三、四种基础策略：为什么「删除」而非「更新」

四种同步顺序，逐一判死刑：

| 策略                 | 第二步失败后果              | 并发问题                       | 结论            |
| ------------------ | -------------------- | -------------------------- | ------------- |
| ① 先更新缓存，再更新 DB     | 缓存是**脏数据**（新值，DB 没落） | 永久不一致                      | 最差，没人用        |
| ② 先更新 DB，再更新缓存     | 缓存是**旧数据**           | **写覆盖**：两个写交错，最后写的缓存可能是中间态 | 不推荐           |
| ③ 先删缓存，再更新 DB      | 缓存是**空数据**（DB 没更成）   | 并发读回填旧值（见第四节）              | 次优            |
| ④ **先更新 DB，再删除缓存** | 缓存是**旧数据**，但下次读会回填新值 | 窗口极窄                       | **黄金组合，默认选择** |

**为什么是删除而不是更新缓存？** 三个理由：

1. **删除是无状态，更新是有状态。** 删除只需要知道 key；更新需要拿到「新值」，而这个新值往往是更新 DB 时的入参，多一次计算/传输，还可能是错的。
2. **并发写会写覆盖。** 请求 A 更新缓存为值 v1，请求 B 更新缓存为值 v2，但 DB 最终落的是 v2 还是 v3 取决于交错顺序，缓存可能永远停在中间态。删除则没有这个问题——删完下次读自然回填最新的。
3. **可能缓存了没人读的数据。** 一个写多读少、甚至写完再也不读的 key，更新缓存是纯浪费；删除则按需回填（惰性加载）。

> **删除的额外红利**：缓存删了、下次读才回填，天然形成「惰性加载」，冷数据不会常驻内存。更深一层：**删除让 DB 永远是唯一真相源（single source of truth），缓存只是可随时重建的副本**——这是「删不更新」能被默认接受的根本原因。

## 四、两种并发时序漏洞：黄金组合也不完美

### 漏洞 A：先删缓存，后更新 DB（策略 ③）

```
请求 A（写）                    请求 B（读）
  │ 1. 删除缓存
  │                             2. 查缓存未命中 → 查 DB 读到旧值
  │                             3. 把旧值回填缓存
  │ 4. 更新 DB 为新值
  └── 结果：DB 是新值，缓存是 B 回填的旧值 → 脏数据
```

漏洞本质：**「删缓存」和「更新 DB」之间，读请求进来把旧值又填回去了。** 窗口 = 两次 DB 操作之间，概率较高，所以策略 ③ 不推荐。

### 漏洞 B：先更新 DB，后删缓存（策略 ④，黄金组合的尾巴）

```
请求 A（读）                    请求 B（写）
  │ 1. 查缓存未命中
  │ 2. 查 DB 读到旧值（还没回填）
  │                             3. 更新 DB 为新值
  │                             4. 删除缓存
  │ 5. 把旧值回填缓存
  └── 结果：DB 是新值，缓存是 A 回填的旧值 → 脏数据
```

漏洞本质：**A 必须在 B「删缓存」之后才完成回填**，而 A 读 DB 是在 B 更新 DB 之前。这要求读请求极慢、恰好卡在「删缓存」之后才回填，**窗口极窄（纳秒到毫秒级），概率极低**——所以策略 ④ 是工程默认。

> 判断力要点：两个方案都有洞，选的是**洞更小、概率更低**的那个，而不是「无洞」的（不存在无洞方案）。

## 五、延迟双删：延迟多久？以及它补不了什么

延迟双删的流程在第二节，它补的是漏洞 B 里「读请求回填脏数据」这个尾巴——第二次删缓存把回填的旧值清掉。

**延迟多久？** 字节一面的经典追问（[知乎原文](https://zhuanlan.zhihu.com/p/6262725224)）。经验值：

- 覆盖「读请求从查 DB 到回填缓存」的业务耗时 + 「主从同步延迟」（读写分离时读从库） + 冗余。
- 常见取值 **几百 ms ~ 1s**；有实践用「1.5 倍冗余系数」覆盖 P99 耗时毛刺。
- **过短 → 脏数据没清掉；过长 → 不一致时间被拉长。** 没有万能值，只能按业务监控的 999 分位耗时来调。

**延迟双删补不了什么：**

1. **强一致**——延迟期间本身就是不一致窗口，只是缩短了，不是消除。
2. **删除失败**——第二次删也可能失败，这才是下一层（MQ 重试 / binlog CDC）要解决的。
3. **主从延迟的根本问题**——延迟双删只是「等一会儿」，治标。

### 5.1 异步延迟双删（工业界落地标准）

第二次删除不该阻塞请求主流程，而是异步执行（丢给线程池 / MQ 延时消息），失败再进重试队列。这样「延迟」只影响最终一致性的收敛时间，不影响写接口的 RT。

### 5.2 读写分离下，主从延迟是新的坑

一旦 DB 做了主从读写分离，先更库后删缓存就多一条脏数据路径：

```
请求 A（写）                    请求 B（读）
  │ 1. 更新主库为新值
  │ 2. 删除缓存
  │                             3. 查缓存未命中 → 读【从库】拿到旧值（主从还没同步）
  │                             4. 把旧值回填缓存
  └── 结果：DB（主）是新值，缓存是 B 从从库读到的旧值 → 脏数据
```

根因：**删除缓存后，读请求可能命中还没同步完的从库**，把旧值填回来。这解释了延迟双删为什么要「等主从同步完成」。

两条解法：

| 解法           | 说明                     | 代价             |
| ------------ | ---------------------- | -------------- |
| 延迟双删覆盖主从延迟   | 延迟时间 ≥ 主从同步耗时，第二次删清掉旧值 | 治标，主从延迟波动时仍可能漏 |
| 关键读走主库（强一致读） | 一致性敏感的数据从主库读，绕开从库延迟    | 主库读压力上升，需按场景收敛 |

## 六、删除失败怎么办：三层兜底

删除是最终一致性的关键动作，删失败 = 脏数据常驻（直到缓存过期）。三层兜底：

| 层            | 机制                                 | 说明                                   |
| ------------ | ---------------------------------- | ------------------------------------ |
| ① 缓存过期时间     | TTL 到期自动失效                         | 最后的防线；但过期时间要**随机**（防雪崩），且脏数据在过期前一直存在 |
| ② MQ 重试      | 删除失败 → key 进 MQ → 消费重试             | 保证「删除」最终被执行；代价是引入 MQ                 |
| ③ binlog CDC | Canal/Maxwell 监听 binlog → MQ → 删缓存 | 解耦 + 兜底，覆盖所有写路径；代价是两套中间件             |

> **演进逻辑**：过期时间是「总会失效」的兜底，MQ 是「主动删干净」的兜底，binlog CDC 是「不依赖业务代码、覆盖所有写源」的兜底。越往上层越可靠，成本也越高。

## 七、最终一致 vs 强一致：怎么选

把结论收敛成一张决策表：

| 场景                 | 一致性要求     | 方案                               |
| ------------------ | --------- | -------------------------------- |
| 文章详情、排行榜、商品详情（热点读） | 允许秒级延迟    | 先更库后删缓存 + 过期时间兜底（最简）             |
| 需更稳、写路径多           | 最终一致      | 先更库后删缓存 + 延迟双删 + MQ 重试           |
| 缓存即数据副本、要求低延迟同步    | 最终一致（近实时） | binlog CDC（Canal → MQ → 删缓存）     |
| 库存、余额、订单状态         | **强一致**   | DB 事务 + 条件写/版本号，缓存只读旁路；必要时分布式锁串行 |

**高并发优化：热点 key 永不过期。** 秒杀商品、爆款详情这类热 key，不设 TTL，靠 binlog CDC 同步更新/删除来保持一致——避免 TTL 到期瞬间大量请求同时回填导致缓存击穿。代价是必须依赖 binlog 链路可靠，且 key 会常驻内存。

**最后的判断力问题：能不能不用缓存？** 和分布式锁那篇的结论一致——先问「这个缓存是不是必须的」。读多写少、有热点、可容忍延迟，才引入缓存；引入了就要为它的一致性债务买单。

## 附录 A：大厂面试题清单（自测）

1. **双写一致性有哪几种策略？各有什么问题？** → 四种同步顺序 + 结论（先更库后删缓存）。
2. **为什么是删除缓存而不是更新缓存？** → 无状态/并发写覆盖/可能没人读。
3. **先更新 DB 再删缓存，会不会有不一致？** → 漏洞 B 的极端窗口（概率极低），用延迟双删兜。
4. **延迟双删要延迟多久？** → 覆盖回填耗时 + 主从延迟 + 冗余，按 999 分位调。
5. **删缓存失败了怎么办？** → MQ 重试 / binlog CDC / 过期时间兜底。
6. **读写分离（主从延迟）下，双写一致性有什么新坑？** → 读从库拿到旧值回填，延迟双删要等主从同步。
7. **库存/余额这类强一致场景怎么处理？** → 不走缓存双写，DB 事务 + 条件写，缓存只读旁路。
8. **Canal 方案是什么？为什么能解耦？** → binlog 订阅 → MQ → 异步删缓存，业务零侵入。
